    Session 13

    Blockchain 101

    Goal: a shared mental model. A blockchain is a ledger many computers keep, anyone can check, and no one can quietly edit. Everything is built from hashes, signatures and consensus.

    Open deck Terms
    Deck00 · Open

    What a blockchain is

    • Working definition: a ledger replicated across many independent computers. Anyone can check the history; no single party can rewrite it without being caught.
    • The problem it solves: double-spending without a trusted middleman. The digital version of the Byzantine Generals problem.
    • Tonight uses three primitives they already know from the program: hashes, signatures, consensus.
    Deck01 · Hash

    Hash functions

    • SHA-256 for Bitcoin, Keccak-256 for Ethereum. Any input, any size, fixed 256-bit output.
    • Three properties: deterministic, infeasible to reverse, collision resistant.
    • Avalanche effect: on screen, "0.50" and "0.51" differ by one bit, and 136 of 256 output bits change.
    • Merkle trees: hash pairs of transactions up to one root, so one root commits to every transaction in the block.

    You cannot nudge a record and keep its fingerprint.

    Deck02 · Order03 · Chain

    Blocks and the hash link

    • A hash fingerprints one record. A blockchain also needs order: if I sign two payments with the same coins, the network must agree which counts.
    • Blocks are the unit of ordering: height, timestamp, list of transactions, identified by their own hash.
    • The core trick: each block header stores the hash of the previous block, back to genesis. Change anything old and the next block stops pointing at it.
    • Same structure as Git commits or a tamper-evident audit log.
    Deck04 · Mempool

    From wallet to block

    • A user signs in a wallet and broadcasts. Nodes check signature and nonce, then hold it in the mempool, a public waiting room.
    • Public mempool is a security issue: anyone sees your transaction before it confirms. Root of front-running (Session 16).
    • Ethereum: 12-second slots, one validator per slot chosen by stake. It picks by fee, executes, publishes the new state root; others attest.
    • Finalized after two epochs, about 13 minutes.
    Deck05 · Consensus

    Who adds the next block

    • Proof of Work (Bitcoin): solve a costly hash puzzle. Rewriting history means redoing the work faster than the honest network. Security is energy spent.
    • Proof of Stake (Ethereum since the Merge, September 2022): lock at least 32 ETH; sign two conflicting blocks and get slashed. Energy use fell by more than 99%.
    • The limit: a majority of hash power or stake can censor and reorder recent, not-yet-final blocks. Ethereum Classic suffered 51% attacks in 2019 and 2020.

    For any chain: how expensive is it to get the majority, and what does finality guarantee?

    Deck06 · Tamper

    Live tamper evidence

    • Someone edits one transaction in block 26,104,903. Its fingerprint changes; block 904 still holds the old one; every later block falls out of proof.
    • To hide it, the attacker must recompute every later block and out-pace the network: the majority attack from the last slide.

    Tamper evidence, not tamper prevention.

    Deck07 · Signature

    Keys are the identity

    • A transaction: sender, recipient, value, nonce, signature. ECDSA over secp256k1, the same curve as Bitcoin.
    • Address = last 20 bytes of Keccak-256 of the public key. No username, no password.
    • Any node verifies the signature with the public key, recovered from the signature itself. That is where the "from" address comes from.
    • The nonce, a counter per account, stops replay of the same signed transaction.

    Whoever holds the key owns the account. No helpdesk, no reset, no chargeback.

    Deck08 · Threats

    What the chain does not protect

    • Strong: integrity and availability. Not given: confidentiality. Everything is public by default.
    • Keys: Bybit, February 2025, about 1.5 billion dollars, through a compromised signing interface, not broken cryptography.
    • Contract logic: The DAO, 2016, about 3.6 million ETH, a re-entrancy bug.
    • Bridges and oracles: Ronin, 2022, about 625 million dollars, 5 of 9 validator keys taken.

    Most losses happen around the chain, not inside it.

    Deck01 · Compile

    Bytecode and ABI

    • Solidity is not what runs on chain. The compiler produces two artifacts: EVM bytecode (deployed) and the ABI (a JSON menu of functions).
    • Deployed code is capped at 24,576 bytes by EIP-170. Why large systems split into several contracts or use proxies.

    Bytecode is what runs. The ABI is how anyone talks to it.

    Deck02 · Transaction03 · Mempool04 · Block

    A deploy is just a transaction

    • No special deploy command: an ordinary transaction with an empty "to" field and the init code as data. Same mempool, same gas, same blocks.
    • The wallet signs; the transaction waits in the mempool with everyone else's.
    • Blocks hold an ordered list and point at the previous hash (Session 13). Order matters: two transactions on the same contract give different state depending on which runs first. That is where front-running lives.
    Deck05 · Address

    Where the contract lands

    • Receipt status 1 means success.
    • The contract address is not random: last 20 bytes of keccak256 of RLP(deployer, nonce). Anyone can predict it before you deploy.
    • CREATE2 offers a salt-based alternative; it matters later for counterfactual wallets.
    Demowallet-flow.htmlabout 8 min

    How a wallet connects a page to the chain

    Use this before the Interact scene. Press Play, or step with the arrow keys. Toggle MetaMask and Brave Wallet in the top right: both behave the same.

    1. Connect (steps 1 to 3)

      The page knocks on window.ethereum. You approve. Only the address is shared; the key never leaves the wallet. Then the page checks the chain ID.

    2. Read (steps 4 to 6)

      eth_call with the selector 0x8381f58a for number(). The node runs the bytecode in its EVM and throws the result away. Free, no signature.

    3. Write (steps 7 to 12)

      Increment becomes data 0xd09de08a. The page can only ask; the wallet shows the prompt, you confirm, it signs inside. The signed bytes go to a node, wait in the mempool, land in a block, and every node's EVM moves 7 to 8.

    The page asks, the wallet signs, the node relays, the chain decides.

    Step 8, the confirm prompt: what should you read before pressing Confirm?

    Deck06 · Interact

    Call, send, verify

    • Call (eth_call): one node, current state, no transaction, no fee, no signature. Cannot change state.
    • Send: a signed transaction whose data starts with the 4-byte function selector. Pays gas, gets mined, changes state for everyone. The nonce goes up by one.
    • Verify: until verified, the explorer shows only bytecode. Verification publishes source and compiler settings so the explorer can recompile and match.

    Treat an unverified contract as unreadable: you are trusting code you cannot inspect.

    Deck07 · Signature

    Inside a signed transaction

    • Fields: nonce, gas settings, to, value, data, chain ID. There is no "from" field: the sender is recovered from the signature.
    • Every node recovers the public key, derives the address, checks nonce and balance.
    • EIP-155 puts the chain ID inside the signed data, so a testnet transaction cannot be replayed on mainnet.
    Deck08 · ABI

    The ABI is your attack surface

    • One question per write function: who can call this? reset, withdraw and transferOwnership check msg.sender against the owner.
    • Delete onlyOwner from withdraw: the ABI does not change. Same name, same selector. Only the source shows the check is gone, and anyone can drain it.
    • Same lens for tokens: an unlimited approve() to a malicious spender is how most wallet-drainer phishing works.

    One missing modifier on one line is a classic real-world loss.

    DemoKit terminalabout 15 min

    Hello World, from zero to live

    1. Create it

      make new-dapp NAME=HelloWorld

      Walk src/HelloWorld.sol: message, the immutable owner, setMessage, the MessageChanged event.

    2. Write the greeting

      In script/HelloWorld.s.sol: new HelloWorld("Hello, World!").

    3. Test before deploying: it cannot be edited later

      forge test --match-contract HelloWorldTest -vv

    4. Deploy locally

      make deploy NETWORK=local CONTRACT=HelloWorld

      Point at the printed address and the entry in web/deployments.json.

    5. Read it: a call, free

      cast call <address> "message()(string)" --rpc-url http://127.0.0.1:8545

    6. Write it: a transaction, signed

      Reload localhost:3000, open HelloWorld, send "Hello, AIM!", confirm in MetaMask, show the MessageChanged entry. Connect this back to the wallet animation.

    7. Publish and verify on Prismo

      make deploy NETWORK=prismo CONTRACT=HelloWorld
CONSTRUCTOR_ARGS=$(cast abi-encode 'constructor(string)' "Hello, World!") make verify CONTRACT=HelloWorld

      Open the explorer link: transaction, verified source, message under Read Contract. Ask students to open it on their phones.

    Anyone in the world can now read this contract.

    Verification fails if the string in CONSTRUCTOR_ARGS differs from the deploy script by even one character.

    Session 15

    Digital identity

    Goal: what changes when the holder carries the proof, and what the blockchain does and does not do in that picture. Then prove it live.

    Open deck DID animation Terms
    Before class
    • Deploy the DID contracts once: make did STEP=setup NETWORK=prismo, then make verify CONTRACT=DIDRegistry and make verify CONTRACT=StatusList.
    • If you rehearsed, run make did STEP=reset NETWORK=prismo so the demo starts with a fresh student.
    • Open did-flow.html in a second tab.
    Deck00 · Open

    Identity today is silos

    • Your identity is accounts in other people's databases: bank, university, government portal, social login.
    • Each silo is a breach target, each asks for more data than it needs, and you cannot prove a fact about yourself without the silo answering for you.

    How many organisations hold a copy of your passport number?

    Deck01 · Credentials

    Issuer, holder, verifier

    • The issuer signs a claim, the holder keeps it in a wallet, the verifier checks the signature.
    • W3C Verifiable Credentials Data Model 2.0: Recommendation since May 2025.
    • The verifier never contacts the issuer. That is the privacy property we want.
    Deck02 · DID

    Decentralized Identifiers

    • A DID is a URI that resolves to a DID document: public keys, service endpoints, who controls it. DID Core 1.0, W3C Recommendation since July 2022.
    • did:ethr: the identifier is an Ethereum address; changes are events in an ERC-1056 registry, ordered and timestamped by block height.
    • did:web uses DNS instead of a chain.

    For each DID method: which trust root does it really rely on?

    Deck03 · Registry

    What goes on chain, and what never does

    • On chain: public keys, key rotations, delegate grants, hashes, revocation status.
    • Never: names, dates of birth, document numbers, the credential itself.
    • A chain is append-only and public: personal data written there cannot be erased, which conflicts with GDPR.

    If a hash of personal data is on chain, is it still personal data? (Often yes, when the input space is small.)

    Deck04 · Revocation

    Status lists and herd privacy

    • Credentials must be revocable: a diploma issued in error, an employee who leaves, a stolen device.
    • A status list is a long bitstring; each credential owns one index. The issuer flips the bit and anchors the update.
    • The verifier fetches the whole list, shared by many credentials, so the check does not reveal which holder is verified: herd privacy. List size matters.
    Deck05 · Tamper

    Attacking the registry

    • An attacker edits a key entry in an earlier block to swap in their own key and impersonate the owner.
    • The entry's hash changes, the next entry stops pointing at it, every later entry falls out of proof.

    The registry's integrity holds. The weak points are elsewhere.

    Deck06 · Credential

    One credential in detail

    • A Bachelor of Science from a university under did:web. The claims sit in the credential, held by the student, not on any chain.
    • The verifier resolves the issuer DID, gets the key, checks the signature. The issuer never learns where the credential was used.
    • If the issuer key is compromised, every credential it signed is in doubt.

    Key management is the real security boundary.

    Demodid-flow.htmlKit terminalabout 20 min

    Issue, verify, tamper, rotate, revoke

    For each beat: show the animation step first, then run the command. Add NETWORK=prismo to every command.

    1. Every address is already a DID (animation step 1)

      make did STEP=resolve

      Empty history. Creating a DID costs nothing and needs no transaction.

    2. The university issues (steps 2 to 3)

      make did STEP=issue

      Read the header, claims and status index aloud. No transaction was sent: the credential lives with the student.

    3. The employer verifies (steps 4 to 6)

      make did STEP=verify

      Three checks, VALID, and "university contacted: no". That line is the whole point of the session.

    4. The student upgrades BSc to PhD (steps 7 to 8)

      make did STEP=tamper

      Key found, signature fails. REJECTED. One changed letter is enough.

    5. The university adds a new key (step 9)

      make did STEP=rotate

      Open the transaction on the explorer. The DID document now lists two keys, and the history shows the block.

    6. The key was stolen: retire it

      make did STEP=retire

      The credential signed with that key is REJECTED. This is the threats slide in one command.

    7. Revoke the original credential (steps 10 to 11)

      make did STEP=revoke

      Key and signature still pass; the status bit fails. REJECTED, and still no call to the university.

    Is this JWT format standard? The structure is. The signature uses Ethereum message signing so cast can check it; production wallets use ES256K or EdDSA through libraries such as did-jwt-vc.

    Deck07 · Disclosure

    Selective disclosure

    • The holder reveals only what the verifier needs. SD-JWT hides each claim behind a salted hash and reveals chosen ones.
    • BBS signatures and zero-knowledge proofs go further: prove "over 18" without showing the birth date.
    • Withheld claims never leave the wallet. (Not in the live demo.)

    What stops a verifier from asking for everything anyway? (Policy and wallet UX, not cryptography.)

    Deck08 · Threats

    Threat model

    • Key theft from the holder wallet: hardware-backed keys.
    • Phishing for presentations by a fake verifier: verifier authentication, clear consent screens.
    • Issuer compromise: key rotation and revocation. (They just watched both.)
    • Correlation across verifiers from a reused DID or signature: pairwise DIDs, unlinkable proofs.
    • Lost device: plan recovery before it happens, social or custodial, each with a trade-off.

    From research to production

    • eIDAS 2.0, Regulation (EU) 2024/1183, in force since May 2024: every Member State must offer an EU Digital Identity Wallet, deadline end of 2026.
    • The three silos from the start become three credentials in one wallet.

    Session 16

    Gas and Q&A

    Goal: how gas is counted, how it is priced, and how attackers use it. Then close the four sessions as one stack.

    Open deck Terms
    Deck00 · Open

    Why gas exists

    • The EVM is Turing-complete, so no node can know whether a call will finish: the halting problem.
    • Gas meters every step and stops execution when the budget runs out.
    • The same meter blocks denial of service (spam costs money) and pays the validators.
    Deck01 · Cost

    21,000 gas

    • The cheapest transaction, a plain transfer, costs exactly 21,000 gas: the intrinsic cost before any code runs.
    • Keep two numbers apart: gas units measure work; gas price in gwei is what you pay per unit. One gwei is a billionth of an ETH.
    Deck02 · Budget03 · Blocks

    Block budget and rollups

    • Mainnet block limit: 60 million gas (raised from 30M during 2025; Fusaka default). EIP-1559 target is half.
    • Above target the base fee rises, at most 12.5% per block; below target it falls. A raise toward about 200M is being tested with Glamsterdam: check the live figure before quoting it.
    • Blocks fill by gas, not transaction count: same 31.2M gas, 1,486 transfers or 4 contract calls.
    • Rollups move execution off mainnet. Since Dencun (March 2024), EIP-4844 blobs are a separate, cheaper fee market. Prismo Glassnet, where we deployed, is one of these rollups.
    Deck04 · Mempool

    Bidding for space

    • Each pending transaction names a max fee and a max priority fee (the tip). Builders sort by what they earn.
    • The low-tip contract deploy that needs more gas than is left waits for the next block.
    • The base fee is burned; only the tip goes to the validator. That removes the incentive to stuff blocks with fake transactions.
    Deck05 · Attacks

    Gas as a security boundary

    • Unbounded loops: a loop over an array anyone can grow eventually needs more gas than a block holds, and never runs again. GovernMental (2016) froze its jackpot this way. Fix: bound loops, or let users pull.
    • Gas griefing: out of gas reverts state but not the gas spent. Supply just enough for the outer call while the inner one fails. Check every low-level call's return value.
    • Front-running and sandwiches: the public mempool lets anyone outbid you. Defences: commit-reveal, slippage limits, private relays.

    Which of these did we already see in Session 13 or 14? (Public mempool, transaction order.)

    Deck06 · Fee

    Work one fee out loud

    • 21,000 gas × (12 gwei base + 2 gwei tip) = 294,000 gwei = 0.000294 ETH. The rectangle: height is gas, width is price.
    • Split it: 21,000 × 12 gwei burned, 21,000 × 2 gwei to the validator.
    • If the base fee rises past the max fee the transaction waits; unused max fee stays in the wallet.
    • Prices are illustrative; recent mainnet base fees are often far lower and spike under demand.
    Deck07 · Opcodes

    What each operation costs

    • ADD costs 3 gas. A storage read costs 2,100 cold and 100 warm (EIP-2929).
    • Writing a non-zero value into an empty slot costs 20,000, plus 2,100 if cold.
    • Storage is the expensive part: keep state small, cache reads in memory.
